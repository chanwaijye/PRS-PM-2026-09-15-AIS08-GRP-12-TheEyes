# calibration — intrinsics, extrinsics, world registration ★

Produces `config/extrinsics.yaml` (`INTERFACES.md` §4), the file fusion
refuses to start without.

## Build and test

```bash
cmake -S SystemCode -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j"$(nproc)"
ctest --test-dir build --output-on-failure

build/calibration/calibrate mock /tmp/extrinsics.yaml    # full run, no cameras
```

`opencv_aruco` (from opencv_contrib) is **optional**. ChArUco *detection* needs
it; the solver does not, because it works on `BoardObservation`s that synthetic
generation can produce. So the calibration maths is fully testable on a machine
with no contrib, no cameras, and no images.

## Mock mode is the primary development mode

Synthetic observations are generated by projecting the board's known corners
through a known camera pose, then handed to the solver, which must recover what
went in. That validates the solver independently of detector quality, lens
distortion, and lighting — none of which exist yet.

Verified: intrinsics recovered to **fx/fy within 1 px** and **cx/cy within 2 px**
from noiseless views; RMSE under 0.5 px with realistic 0.2 px corner noise;
distortion coefficients recovered to ±0.02.

## The board

**8 × 8 squares at 38 mm**, `DICT_5X5_250`, 49 interior corners, 32 markers, on
a 324 × 324 mm panel. Arrived 2026-08-28.

Confirmed on the physical board, from a real capture: markers decode under
`DICT_5X5_250` with ids 0–31, i.e. 32 markers, i.e. 8 × 8 squares. **The square
length is still `[VERIFY]`** — callipers across eight squares divided by eight,
not one square. That value scales every distance in the system while every
reprojection error stays small.

### It only decodes at 1920 × 1080 — capture there

A `DICT_5X5` marker is 7 modules across and stops decoding below ~3 px/module.
Sizing this board against the 0.70 m standoff is the mistake: the board lies
flat and the cameras are oblique at 35°, so its **far corner sits 884 mm away**.
Against the measured factory colour intrinsics:

| capture | fx | px/module @ 0.884 m | reach | |
|---|---|---|---|---|
| 848 × 480 (streaming) | 603.43 | 2.8 | 0.82 m | fails |
| 1280 × 720 | 905.15 | 4.2 | 1.23 m | ok |
| **1920 × 1080** | **1357.72** | **6.3** | **1.84 m** | 2× margin |

Measured reach at 1920 × 1080 on this rig: **1.85 m** (`261722073945`) and
**1.84 m** (`261822074567`).

The recovered camera *pose* is resolution-independent — same projection centre,
differently sampled — so captures taken at 1080p stay valid while the pipeline
streams 848 × 480. That is what `run --factory` is for, and on this rig it is
mandatory rather than optional. `BoardSpec::MaxDecodeDistance` computes the
reach and every subcommand prints it **before** detecting, because a board that
cannot decode returns zero corners from images that look perfectly good.

## Factory intrinsics — you probably do not need a precision board

The D400 carries genuine **per-unit** factory calibration (measured here:
fx 607.01 for `261722073945` vs 603.43 for `261822074567` — real values, not a
generic default), and reports **zero distortion** on the colour stream because
it comes out rectified.

The main prize in a 40-view intrinsic sweep is the distortion model, and there
is none to recover. So `FactoryIntrinsics()` lets you skip the sweep and solve
only the extrinsics.

**What the factory cannot give you is the transform between the two cameras.**
That depends entirely on how you mounted them, and it is the thing this project
rests on. It has to be solved locally, always.

That changes what the target must do:

| step | needs | target demands |
|---|---|---|
| intrinsics | ~40 views, varied distance and tilt | large, dimensionally accurate |
| extrinsic registration | **one** view both cameras can see | flat, and correctly measured |

So a paper print laminated onto foam board, acrylic, or glass is enough —
**flatness and a callipered square size matter, precision machining does not.**
A metrology-grade target buys accuracy far past what an 848×480 sensor resolves.

Quality is then gated differently: a factory result has no calibration views, so
the view-count check is skipped and the **registration view** becomes the gate —
it exercises the factory intrinsics against real corners, so bad factory values
still show up. That registration RMSE is also what gets written to
`extrinsics.yaml` as fusion's gate, because writing 0.0 would hand fusion a
meaningless pass.

## Usage on the real rig

```bash
# 1. sweep: board handheld, varied distance and tilt. ENTER shoots, q finishes.
build/calibration/calibrate capture config/cameras.yaml config/calibration.yaml captures

# 2. registration: board at its MEASURED world position, both cameras at once.
build/calibration/calibrate capture config/cameras.yaml config/calibration.yaml captures --register

# 3. solve
build/calibration/calibrate run config/calibration.yaml \
    captures/cam_front <front_serial> captures/cam_over <over_serial> \
    config/extrinsics.yaml --factory
```

`capture` writes `captures/<camera_id>/view00.png…` for the sweep and
`zz_register.png` for the registration view — named so it sorts **last**,
because `run` takes the alphabetically last image in each directory as the
registration frame. It detects every frame as it is saved and prints the corner
count, a relative sharpness figure, and the shared-corner count across the two
cameras. Finding out that a capture set yields no corners has to happen while
the board and the lighting are still where they were.

Re-running against an existing directory **extends** the sweep rather than
overwriting it.

### capture opens the colour stream only

Not an optimisation — a hardware limit measured on this rig. Two D435i units
**cannot both run 1920 × 1080 colour and 848 × 480 depth simultaneously**: the
second `pipeline.start()` blocks indefinitely, at 30 fps and at 15. Colour only,
both start in ~0.2 s and deliver frames. ChArUco corners come from the colour
sensor, so nothing is lost.

The consequence to know: the inter-camera sync trigger drives the **depth**
sensor, which is closed in this mode, so the two colour streams are
free-running. Measured pair skew is one frame period or less. It does not matter
for a stationary board, which the registration shot is.

`StreamConfig::color_only` carries this; it is set by the tool, not by
`cameras.yaml`, because it is a capture mode rather than a property of the rig.

**Print at 100% and measure a square with callipers.** Printer scaling is the
classic silent failure here: every reprojection error stays small while every
distance is wrong by a constant factor, so the calibration looks excellent and
every fused pose is scaled wrong.

**Calibrate after final rigid mounting, and re-run after any mechanical
change.** Nothing downstream can detect that the cameras moved — every fused
pose simply becomes wrong by a fixed offset while staying perfectly
self-consistent. The generated file carries this warning in its own header.

## Why the round-trip check exists

Per-camera reprojection RMSE only says each camera is consistent *with itself*.
Two cameras can each be internally perfect and still disagree about where a
point is in the world, because that depends on the registration between them.

`ComputeRoundTrip` takes corners visible to both cameras, pushes each into the
world frame through its own extrinsics, and measures the disagreement.
`Report.RoundTripCatchesAMisregisteredCamera` injects 2 cm of extrinsic error
and asserts that **every per-camera RMSE stays under 0.5 px** while the round
trip catches it. That is the whole argument for the check.

### It measures rays, not model points — [FIXED 2026-08-28]

For each corner both cameras resolved, the two **observed** pixels are
undistorted into world-frame sightlines and the check reports how far apart
those rays pass — their closest approach. Zero means the sightlines intersect,
i.e. the two views agree exactly about where that corner is.

This replaces an implementation that was **degenerate in the real path**, and
the reason is worth keeping written down. It pushed the board *model* point
through each camera's extrinsics; but `T_world_cam` is itself derived as
`T_world_board * pose.T_cam_board⁻¹` from that camera's PnP of the same
observation, so both sides reduced to `T_world_board * board_point`. The error
was **exactly zero however bad the calibration was**. Observed on a real capture
whose registration RMSE was 3.12 px and 1.89 px: `0.00 / 0.00 / 0.00 mm`. The
same capture through the ray version reports `2.12 / 4.49 / 5.94 mm` and
correctly trips the 5 mm gate.

`Report.RoundTripCatchesAMisregisteredCamera` never caught it because it injects
its 2 cm into `T_world_cam` *after* `RegisterToWorld` — a condition the
production path never creates. Two tests now pin the properties that matter:

| test | property |
|---|---|
| `RoundTripIsNotZeroByConstruction` | rig built exactly as `RunReal` builds it, 0.3 px corner noise, nothing perturbed afterwards — the disagreement must be strictly positive and sub-millimetre. Fails against the old implementation. |
| `RoundTripMeasuresTheRigNotTheWorldPlacement` | moving `T_world_board` leaves the number unchanged to 1e-9. It asks whether the two cameras agree with *each other*; where the board was declared to sit is a rigid transform on both and cannot be validated by any calibration. |

Using the detections is also what makes it blind-spot-free where per-camera RMSE
is blind: a **planar-target pose flip**, where one camera's PnP lands on the
mirror solution, reprojects well and still points its rays somewhere else
entirely.

Distrust this number first when fused poses look wrong.

## Things worth knowing

**The board defines the world frame.** `world.T_world_board` in
`config/calibration.yaml` is the board's measured placement, and every camera
pose derives from it. An error there is a rigid offset on the entire system,
invisible to every downstream check because everything stays self-consistent.
It carries a `[VERIFY]`.

**Corner ids travel with corner points.** ChArUco reports a *subset* of corners
— whichever markers resolved. Pairing that subset positionally against a full 3D
grid is the classic ChArUco bug: it silently associates image points with the
wrong 3D points, and the calibration converges to something plausible and wrong.
Everything here pairs by id.

**This is the OpenCV 4.6 aruco API.** OpenCV 4.7 moved ChArUco into `objdetect`
with a different interface (`CharucoDetector`, `ArucoDetector`). Code copied from
current tutorials will not compile against 4.6, which is what this machine has.

**Too few views is the most misleading failure.** Intrinsics from a handful of
views fit noise, and the reported RMSE comes out *low* precisely because the
solution is under-constrained. `CalibrateIntrinsics` refuses below
`min_views_for_intrinsics`. Vary tilt as well as distance — a stack of
fronto-parallel views leaves focal length and board distance nearly degenerate.

**Self-consistent is not the same as physical.** The first mock scenario placed
both cameras *below the table*: the maths was perfectly consistent, the report
said PASS, and the rig was impossible. `CamerasEndUpAboveTheTableNotBelowIt` now
guards it.

## Session re-registration

The rig mounts cameras on floor tripods and uses a shared computer desk as the
table (`docs/RIG_BOM.md` §A). The desk gets typed on and leaned on, so the
tabletop moves relative to the tripods between sessions. Because the world
frame is glued to the tabletop, that invalidates every `T_world_cam` — and it
is invisible, because every fused pose stays perfectly self-consistent while
being wrong by a fixed offset.

Only `T_world_cam` is affected:

| | rigid to | after the desk moves |
|---|---|---|
| intrinsics | the camera body | unchanged |
| `T_camA_camB` | the tripods | unchanged |
| `T_world_cam` | the tabletop | **changed** |

So one board view per camera, PnP, re-derive. ~30 s instead of a 40-view sweep.

```
calibrate reregister config/calibration.yaml config/extrinsics.yaml out.yaml \
    cam_front:261722073945:front.png cam_over:261822074567:over.png
calibrate reregister-mock          # both outcomes on synthetic poses, no hardware
```

### The check that makes it safe

The arithmetic is the easy part — `RegisterToWorld` already did it. What makes
re-registration usable rather than dangerous is refusing it when it does not
apply. If a **tripod** was bumped rather than the desk, the re-derived poses
are garbage, and writing them out produces an invisible error with a fresh
timestamp on it — strictly worse than the problem being solved.

The two cases are separated by one identity:

```
T_camA_camB = T_world_camA^-1 * T_world_camB
```

is **invariant to the world frame moving**. Recompute it from the new poses and
compare against the stored calibration:

- **unchanged** → the table moved, the rig is intact, re-registration is valid
- **changed** → a camera moved, re-registration is invalid, recalibrate

`reregister-mock` demonstrates why the world-frame numbers alone cannot do
this: in both its scenarios every camera reports the same 13.04 mm of world
motion, and only the baseline separates the recoverable case from the fatal one.

### Design notes

- **All pairs, not a chain.** With three cameras, checking `a-b` then `b-c`
  lets two link errors cancel and passes a rig whose middle camera has rotated.
- **A single camera is refused.** There is no baseline, so the rigid-body
  assumption cannot be tested at all, and re-registration is indistinguishable
  from a bumped tripod.
- **Thresholds are derived, not picked.** `max_baseline_shift_m = 3 mm` sits
  below the 5 mm round-trip gate, so a rig this check passes cannot fail that
  one; the loader enforces the ordering. `max_baseline_rotation_deg = 0.25` is
  `atan(0.003 / 0.70)` — the rotation costing the same lateral error at the
  working distance.
- **Large world motion warns, it does not fail.** The table is *expected* to
  move. But a desk does not slide 20 mm on its own, so a shift that large more
  likely means the board was returned to the wrong spot — which silently
  redefines the world frame, and nothing downstream can detect it. Mark the
  board's origin corner on the tabletop with tape.
- **Serials are checked against the previous file.** A silent serial swap would
  re-register one camera's pose onto the other's id (CLAUDE.md constraint 4).
- **Intrinsics come from the device.** Re-registration does not re-solve them.
  If the original calibration solved its own intrinsics instead of using
  `--factory`, the baseline comparison spans two different K matrices and can
  false-alarm — calibrate with `--factory` if you intend to re-register.
- The previous `extrinsics.yaml` is read through **fusion's own loader**, so a
  file this tool accepts is provably a file fusion will accept, and there is no
  second copy of the INTERFACES.md §4 format to drift.
